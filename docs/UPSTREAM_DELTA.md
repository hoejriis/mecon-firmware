## Duty-cycle enforcement: transmit paths

Every LoRa transmission of the Companion, Repeater, Room-server, sensor and secure-chat roles goes through `Dispatcher::checkSend()`; the only other caller of `startSendRaw()` is the KISS modem, which has its own gate on the same window. Audit of every `startSendRaw`/`startTransmit` call site in `src/`, `examples/` and `variants/`:

| Path | Gated by the window? | Handling |
|---|---|---|
| `Dispatcher::checkSend()`: every Mesh packet (adverts, messages, acks, forwards, discovery, bridge-injected packets, CLI replies) | yes | enforced for Companion and Repeater with the regulatory floor |
| Room server | yes | enforced with the floor, like the Repeater |
| Sensor, secure-chat examples | yes | enforced with the floor: both override `getRadioChannel()` and report the frequency and bandwidth last applied to the radio (the sensor at boot, `tempradio` and its revert; secure chat at boot, since `set freq` applies at the next boot). The sensor and secure-chat roles have no simulated board, so this is covered by a static source check (`sim/tests/test_duty_roles.py`) and by compiling the roles, not by a broker measurement |
| `examples/kiss_modem/KissModem.cpp` (`_radio.startSendRaw`) | yes | every raw send passes the same sliding hour (`src/helpers/DutyWindow.h`, shared with `Dispatcher`) and the regulatory floor of the channel the modem is on. The channel is what the target tuned at boot (`setChannel(LORA_FREQ, LORA_BW)` in `main.cpp`), replaced at once by the host's SET_RADIO. There is no user airtime factor: the floor is the only limit. A frame that does not fit waits in the modem (the host sees TX busy on further data, as for any pending frame) until enough airtime ages out; a frame longer than the whole limit is failed with TX_DONE 0. **Fails closed:** with no known channel the frame is refused (TX_DONE 0) instead of sent unlimited. On a channel with no floor (e.g. 902-928 MHz) nothing is held or counted. Measured at unit level (`pio test -e native_kiss_modem`, radio-side record of key-up times): at most 1 % of any sliding hour at 868.1 MHz and 10 % at 869.525 MHz, 3 h of sustained load |
| `src/helpers/esp32/ESPNOWRadio.cpp` | no | 2.4 GHz ESP-NOW, not subject to the 863-870/433 MHz limits |

Limits of the enforcement: the window lives in RAM and is not persisted; after a boot it is seeded at the limit (see above), which costs a delay before the first transmission: measured 152 s at 868.1 MHz BW 125 (1 %) and 32 s at 869.525 MHz BW 250 (10 %), each including the boot advert's own 16 s delay. A packet put back because it does not fit keeps its place only as "most urgent": the packet manager does not expose a packet's original priority. Airtime is charged as the larger of the estimated time on air and the measured send duration (capped at 1.5 times the estimate).

## Atomic saves: rename behaviour per file system

`AtomicFile` swaps a verified temporary file over the live file. What the platforms are expected to do, from their library sources and documentation, **not yet verified on hardware**:

| Family | File system | Rename over an existing file | What `AtomicFile` does |
|---|---|---|---|
| ESP32 | SPIFFS | Not assumed to replace the destination (SPIFFS reports a name conflict) | Two-step swap: temp file to `<path>.new`, remove `<path>`, `<path>.new` to `<path>`. There is a window with no `<path>`; boot completes the swap from the verified `<path>.new`. The simulated board refuses rename-over to hold the code to this. |
| nRF52, STM32 | Adafruit LittleFS (littlefs) | Atomic replace (`lfs_rename`) | Direct rename over the live file. |
| RP2040 | LittleFS (littlefs) | Atomic replace (`lfs_rename`) | Direct rename over the live file. |

Covered: prefs, identity, the channel table, the contact buckets, the Companion blobs and the client ACL.

Temporary space: a save needs room for one extra copy of the file being replaced. The largest are the client ACL (32 clients of 136 bytes, 4,352 bytes at most), the nRF52 / STM32 blob table (`/adv_blobs`: 20 records of 178 bytes, 3,560 bytes, or 17,800 bytes with 100 records on boards with an extra file system) and a contact bucket. An ESP32 or RP2040 blob is one file of at most 166 bytes. The nRF52 / STM32 blob table path is not built by any simulated environment: it compiles for the RAK4631 Companion, but **no test exercises it**; the ESP32-style `/bl/<key>` path and the ACL are.
